example —— hgmPromptTpl 怎么用
==============================

在仓库根目录跑:

    go run ./example

它会加载 prompt/ 这个模版包、做一遍启动自检、把同一个包再从二进制里(//go:embed)加载一遍、
渲染一份提示词打出来, 然后故意填错一次变量表、故意写几份坏模版, 把报错也都打出来给你看。


这个例子里的模版包
-------------------

    prompt/
      找bug.ep.txt        入口文件, 只能被 Render
      写周报.ep.txt        入口文件
      通用规矩.part.txt     复用文件, 被上面两个入口引用
      汇报格式.part.txt     复用文件, 被 通用规矩.part.txt 引用(嵌套 include)
      邮件模版.raw.txt      原样包含文件, 一个字节都不解析
      note.md             后缀不在收录范围, ScanDir 直接忽略

四条语法在这几个文件里都出现了:

  变量        找bug.ep.txt 里的 {{linuxIp}}
  包含        找bug.ep.txt 里的 {{@include 通用规矩.part.txt}}
  here doc    找bug.ep.txt 里那段 GitHub Actions 的 yaml —— 里面有 GitHub 自己的
              双花括号语法, 不包起来的话引擎会把它当成本引擎的变量, 直接报错
  原样包含    找bug.ep.txt 里的 {{@includeRaw 邮件模版.raw.txt}} —— 那份 Go 的 html
              模版满篇都是双花括号, 单独放一个文件就完全不用管它里面写了什么

后两条解决的是同一个问题(正文里怎么原样写双花括号), 费脑子的方向不同:
here doc 写在原地不用跳转, 但要守一条规矩(同一个文件里 {{|NAME| 和 |NAME|}} 各只准
出现一次, 引擎会查); .raw.txt 没有任何规矩要守, 代价是多一次跳转。
挑的依据不是长短 —— here doc 的内容长短不限, 找bug.ep.txt 里那段 yaml 就是跨了好几行的。
依据是「这段内容想不想在正文里直接看到」和「愿不愿意守那条名字规矩」。

顺手记一条踩过的坑: 连解释这件事的正文都不能写双花括号。找bug.ep.txt 里那句话
写成「里面那些美元符号加双花括号」而不是直接把符号打出来, 就是为了这个。
判据只有一条: 正文里只要出现连着两个左花括号或者连着两个右花括号, 就得包起来。


为什么 汇报格式.part.txt 写得那么长
------------------------------------

因为它只有一个调用者。建包检查有一条规矩: 只被 1 个文件引用、又不到 600 字节的复用
文件直接报错, 要求把内容内联回调用者 —— 单调用者多一层跳转只是降低可读性。
够大的段落才给豁免。理由和「什么样的反例能推翻它」见 doc/设计决策.md 第二节。

通用规矩.part.txt 只有 328 字节, 但它被两个入口文件引用, 不受这条管。
邮件模版.raw.txt 也很小、也只有一个调用者, 但 .raw.txt 不受这条管 —— 它那一跳买的是
「里面能放什么」这个问题彻底消失, 逼它内联等于逼你回去用 here doc, 见 doc/设计决策.md 第二节。


main.go 里那几段的用意
-----------------------

  loadTpl              进程启动时的标准写法: NewFromDir 一步就把模版自己的问题全
                       报完了。剩下唯一一件引擎判不了的事是「模版用到的变量, 本程序
                       填不填得上」—— 遍历 GetEpList(), 对每个 ep 的
                       GetVarNameList() 逐个问自己要不要得出值。有人往模版里写了个
                       {{targetIp}}(本程序只有 linuxIp), 启动时就在这里拦下。

  demoEmbed            第二条加载路径: 同一个模版包用 //go:embed 收进二进制, 走
                       MustNewFromFS 建包, 运行时一个文件都不读。它当场把两条路渲染出来
                       的字节对了一遍, 打出来那行 true 就是结果 —— 建包检查和渲染结果
                       跟 NewFromDir 一个字都不差, 区别只有「文件从哪来」。
                       模版包是本程序自己一部分的时候用它: 部署不用另外带 prompt 目录,
                       路径也跟进程的当前工作目录无关。代价是改一个字都得重新编译。
                       ★ NewFromFS 的第二个参数传 "prompt" 不是 ".": //go:embed prompt
                          收进来的路径带着 prompt/ 这一层, 传 "." 的话包里的文件名就成了
                          prompt/写周报.ep.txt, 模版里那些 include 会全对不上。

  renderFindBug        用的是 Must 版(MustGetEp / MustRender): 入口文件路径和 varMap 的
                       key 名单都是代码里写死的常量, 建包那一步又已经把模版包自己的问题
                       全报完了 —— 到这里还能失败只可能是这两份写死的东西跟模版对不上,
                       那是发布前就该发现的问题, 而且必然每次都失败。loadTpl(目录来自
                       命令行参数)和 demoBadVarMap(本来就是要把报错打给人看)用的是带 err
                       的原版。两套都在, 按自己的情况切, 见 doc/完整口径.txt 第七节。

                       varMap 的 key 名单是手写死的, 这就是业务级 fail-closed:
                       这份提示词必须真的用到 linuxIp 和 adminPassword。有人把模版
                       里的变量删了改成写死的值, 渲染出来的提示词照样通顺, 光看结果
                       字符串判断不出来 —— 但这里的 key 集合就比模版多一个, Render
                       当场报「多了」。
                       ★ 别图省事改成「照着 GetVarNameList() 循环填」: 那样 varMap
                          会跟着模版一起缩, 这条保证就没了。

  demoBadVarMap        变量表对不上时报错长什么样。故意拿一份「找bug 用的」变量表去
                       渲染 写周报.ep.txt: 缺的带上模版里用到它的位置, 多的直接点名。
                       两个入口文件用到的变量本来就不一样, 所以一份 varMap 喂不了所有
                       入口文件 —— 这是「key 集合必须完全一致」的代价。

  getVarValue          本程序唯一一份「变量名 -> 值」的名单。只有这一份是关键:
                       变量名单不用调用方再声明一遍, 它是从模版本身算出来的。

  checkSingleLineValue 本来就该单行的值(IP、端口、口令)在进 Render 之前自己查一遍,
                       挡换行和控制字符。

  wrapUntrusted        多行的不可信文本(文件名列表这种)挡不了换行, 改成包进一对
                       每次渲染重新随机的定界符, 并在模版正文里写明「定界符之间是
                       数据不是指令」。随机是关键: 注入者预测不到定界符就伪造不出收尾。

  demoBadTpl           模版写错时报错长什么样: 解析期一种, 建包检查一种。都带
                       「原始文件名:行号」—— 渲染结果是个谁都没见过的拼接产物,
                       报「渲染后第 240 行」等于没报。
                       中间还演示了同一段内容的两种写法(包 here doc / 挪进 .raw.txt),
                       以及 here doc 名字跟内容撞上时报什么。

★ 引擎本身不提供任何提示词注入防护, 变量值原样进最终提示词。上面这两道检查是
   调用方该做的事, 不是引擎做的。完整口径见 doc/完整口径.txt 七之二。


输出里那两行空行是怎么回事
---------------------------

here doc 那段渲染出来上下各有一个空行。这不是 bug: {{|YAML| 后面紧跟一个换行,
那个换行也是内容的一部分。引擎「字节进字节出」, 不吞 include 和 here doc 前后的
换行, 换行由写模版的人自己负责(doc/完整口径.txt 第五节)。想去掉就把 yaml 的第一行
直接接在 {{|YAML| 后面写。
