# 设计决策

readme.txt 讲的是「怎么用、会报什么错」。这份讲的是「为什么是这样，以及哪些地方是明知有代价
还这么选的」——主要给两种人看：想改这个库的人，和想在别的项目里用它、发现某条规矩不合胃口的人。

每条都写清楚：选了什么、代价是什么、什么样的反例能推翻它。

---

## 一. 正文里的字面量 `{{` / `}}`：here doc 的唯一性检查，外加 `.raw.txt` 这条路

**选了什么**：两条并存，由写模版的人挑。

1. **here doc**：`{{|VUE|...|VUE|}}`。规矩只有一条——**同一个文件里 `{{|NAME|` 和 `|NAME|}}`
   各只准出现一次**（收尾从本块开头之后数起）。内容想跨多少行都行，收尾在哪就管到哪；
   好处是写在原地，不用跳到别的文件。
2. **`.raw.txt` + `{{@includeRaw 路径}}`**：整个文件当字面量，一个字节都不解析。没有任何规矩，
   代价是多一次跳转。

外加一条兜底：here doc 之外不许有裸 `}}`。

### 这一节推翻了原来的结论

原来的方案是「作者自己挑一个内容里没有的名字，引擎用三条启发式**尽量**抓错」：

| | 原来的检查 | 性质 |
|---|---|---|
| a | 闭合之后到下一个 `{{\|` 之前，不许再出现 `\|NAME\|}}` | 启发式，**有盲区** |
| b | here doc 内容里一个 `{{` 都没有 → 它白写了 | 捞「判不了意图」那种 |
| c | here doc 之外不许有裸 `}}` | 兜底，**三条合起来仍有一个洞** |

三条合起来剩的洞是：作者写在末尾的 `|A|}}` 掉进了**后面另一个 here doc 的内容**里，那就是
字面量不是普通文本，c 看不见它。

```
教你写本引擎的模版:
{{|A|变量写作 {{name}}, here doc 收尾写作 |A|}}
正文里的 {{linuxIp}} 会被替换成真值
{{|B|要原样输出就包起来: {{name}} 收尾写 |A|}} 这样|B|}}
```

A 在第二行末尾就闭合了（作者以为它管到第四行）。第三行本该是字面量的 `{{linuxIp}}` 被真的
替换掉，渲染出一份错的提示词，退出码 0。当时的立场是「不堵，写进文档，用测试钉住」，理由是
三种堵法都会把「一个静默错误」换成「一堆误报」。

**那个理由站不住。** 想清楚了两件事：

**第一，here doc 这套本来就是能做对的，问题从来不在正确性。** 内容有限、名字无限，拿「比内容里
最长的那串字母数字再长一个」当名字就一定不撞——这是个确定性的、可计算的规则，任意二进制都塞得
进去。Rust 的 `r#"..."#`、C# 的 `"""`+、C++ 的 `R"delim(...)delim"`、shell 的 `<<'EOF'`、
MIME 的 boundary 全是这一套，全都有正确用法。真正的毛病是：**执行规矩的是人，执行错了没人拦**。
RFC 2046 直接把这件事写成「这是发送方的责任」，然后建议随机；C# 只说「内容里有三个引号就用四个」。
没人查。

**第二，「够长够独特」有一个机器查得动的等价物：唯一性。** 「这个名字在这份文件里，开头和收尾
各只有一个」——这条一 `bytes.Count` 就查完了，而且它把提前闭合从「尽量抓」变成「结构上不可能」：

> 设开头在 p，引擎找到的收尾在 q，作者想要的在 q′。若 q ≠ q′，则文件里至少有两个 `|NAME|}}`，
> 唯一性当场报错。反过来只要过了检查，q 必然等于 q′。

上面那个洞的例子里 `|A|}}` 有两个（第 2 行和第 4 行），不管第二个落在普通文本里还是别人的
here doc 内容里，数数都数得到。a 的盲区（中间夹一个别名 here doc 切断扫描区间）也一起没了——
唯一性根本没有「区间」这个概念。

**误报的代价重新算过。** 原来的表里最担心的是「一份讲多种模版语法的提示词天天这么写」：

| 原来担心的误报 | 重新算 |
|---|---|
| A 正常闭合，后面某个 B 的内容里合法引用了 `\|A\|}}` | 确实会报。但触发条件是**你把一个活着的块，命名成正好等于你例子文本里写的那个名字**——名字按内容取（`VUE`/`GOTPL`/`YAML`）就撞不上，撞上了改个名就行 |
| 同一个文件里两块 here doc 复用同一个名字 | 确实会报，这是真代价，原来是允许的（`TestHereDocSameNameReusedIsOk`）。实测这个仓库的 `example/prompt` 下每个文件只有一块 here doc，代价为零 |

拿「改一次名字」换掉「渲染出一份错的提示词却退出码 0」，值。

**顺带删掉的**：

- **a 删掉**：唯一性严格更强（无区间、无盲区），报错还更具体（能指出是哪几行）。
- **b 删掉**：它兼着兜提前闭合，现在唯一性接管了，剩下的只是风格判断，而且是错的风格判断——
  它挡住了「我就想输出两个字节 `}}`」（`{{|X|}}|X|}}`，实测被 b 拦下），也挡住了「这段外来
  内容今天没花括号，但我不想它以后被解释」。`.raw.txt` 那边显然不会要求内容里必须有 `{{`，
  这边也没道理要求。
- **c 留着**，但降级成最后一格：唯一性堵死的是「写了收尾、引擎在更早处闭合」，还剩一种是
  「压根忘了写收尾，而别处某个 here doc 内容里恰好有一个 `|NAME|}}` 字面量被抓走了」。那时候
  被抓走那块的尾巴会漏成普通文本，里面的 `}}` 是裸的，c 抓得住（`TestHereDocMissingTerminatorStolenFromLiteral`）。

### 为什么还要加 `.raw.txt`

唯一性让 here doc 变成了「有一条规矩，但引擎替你查」。规矩再简单也是一条要理解的东西：你得知道
什么叫收尾、为什么它要唯一、撞上了怎么改。

`.raw.txt` 走的是另一个方向：**根本没有定界符落在内容里**，于是「这里面能放什么」这个问题不存在，
答案永远是「随便」。这是带外框定（out-of-band framing），跟长度前缀（netstring、HTTP chunked）
同类，跟 MIME boundary 那种带内定界相对；比长度前缀强的地方是它还能手改——就是编辑一个普通文本文件。

两条路的成本方向不一样，所以都留着，不替使用者选：

| | 要记的规矩 | 跳转 | 适合 |
|---|---|---|---|
| here doc | 一条（开头/收尾各一次，引擎会查） | 无 | 想跟正文放在一起看的片段（几个字到几十行都行） |
| `.raw.txt` | 零 | 每处一跳 | 整段外来内容（一份 Go 模版、一段 CI 配置） |

**代价**：语法从三条变成四条，模版包里多一种文件后缀。认了——这两条解决的是同一个问题的两端，
少哪一条都会让另一头难受。

**什么能推翻它**：唯一性那条如果在真实模版里造成了一次「明明是对的却被拦下、而且改名不解决」的
误报（不是构造出来的），就得回头重想。或者：如果实践下来两条路里有一条从来没人用，就该删掉那条。

## 二. `PartMinBytes = 600`：单调用者的小 part 必须内联回去

**选了什么**：一个 `.part.txt` 只被 1 个文件引用、内容又小于 600 字节，建包检查报错，要求把内容
搬回调用者并删掉这个文件。

**为什么**：只被 1 个地方引用 = 单调用者，多一层跳转只是降低可读性。但整段大文本内联回去会把
入口文件重新撑成拆分之前那样，所以给一个体量豁免：够大的段落就算只有一个调用者也允许单独放着。
600 字节全中文约 200 个汉字。

**这不是可配置项**。有人会说这是某个项目的团队风格规矩、不是模版语义，应该能关掉。目前的立场是
不关：它跟「一棵展开树里同一个 part 只能出现一次」是同一类东西——都是「这么写一定是写错了」的
断言，而不是口味。可配置只会让它变成一个默认没人开的死开关。

**不想被这条管的正确做法**：把文件名改成不是 `.part.txt`（比如 `xxx.txt`、`xxx.md`），扫描
根本不会收它。想让引擎管的东西才叫 part。

**`.raw.txt` 不受这条管**。这不是漏掉了，是这条规矩的前提对它不成立：「多一层跳转只是降低
可读性」成立的条件是**内联回去不花代价**——对 `.part.txt` 成立（把文字搬回调用者就行）。
对 `.raw.txt` 不成立：那一跳买的是「这里面能放什么」这个问题彻底消失（第一节），逼它内联
等于逼作者回去走 here doc 那条路，而两条路并存、由写模版的人挑是有意的。所以再小的
`.raw.txt` 也放行，只查「没人引用 = 死文件」那一半。

**什么能推翻它**：一个具体的反例——某个 part 天然只有一个调用者、内容也确实短、但内联回去明确
更差。给得出这样的例子就该加开关。目前没有。反过来，如果实践中出现一堆几十字节的 `.raw.txt`
把模版包搅乱了，就该给 `.raw.txt` 也加个下限。

## 三. 跟随目录 symlink（以及由此破掉的一条不变量）

**选了什么**：`ScanDir` 用 `os.Stat` 而不是 `entry.Type()`，所以指向目录的 symlink 会被当成
真目录递归进去。

**为什么**：这是功能不是疏忽。提示词包常要把别处的一份公共段落挂进来。

**代价**：同一个物理文件会有两个 key（`real/x.part.txt` 和 `link/x.part.txt`）。于是 readme
第三节那条「一个 part 只有唯一一种写法」对 symlink 不成立，第四节那个「一棵展开树里同一个 part
只能出现一次」的检查也分辨不出这两个 key 是同一份——从两条路径各 include 一次会照样通过，
同一段内容进最终提示词两遍。

这个代价是明知的。挂 symlink 的人自己保证别从两条路径 include 同一份。

**没选另一条路**：换成 `NewFromFS(fs.FS)` 能让 `os.DirFS(dir)` 和 `embed.FS` 都能喂，而
`fs.WalkDir` 天然不跟随目录 symlink——但那正好把上面这个功能弄没了。embed 的需求目前也没有
（读磁盘是为了改 txt 不用重编译）。真需要 embed 的时候再说，而且到时候要单独想清楚
symlink 怎么办。

## 四. 断链 symlink 一律报错，哪怕后缀不该收

**选了什么**：`os.Stat` 放在后缀过滤之前。所以目录里躺一个断链的 `note.md`（后缀根本不在收录
范围里）也会让整个 `ScanDir` 失败，一份提示词都读不出来。

**为什么**：symlink 断掉之后**看不出它原本指向文件还是目录**。指向目录的话，底下可能整包提示词
都在。按后缀跳过就等于悄悄少读一堆文件，最后表现成「include 找不到目标」，得从那儿一路反查
回来才知道是个断链。目录里躺着断链本身就是环境坏了，当场报比往后拖强。

这跟「别的类型（设备、socket）直接报错而不是跳过」是同一个立场：**静默跳过会让人以为文件没被
收进来是「后缀不对」，白查一轮**。

**代价**：一个跟模版包毫无关系的断链文件能让整个包加载失败。认了。

---

## 五. symlink 指向祖先目录：靠 OS 的 ELOOP，不自己做环检测

readme 里曾经写「已知没管的：symlink 指向自己的祖先目录会无限递归」。**这句是错的**，已改。

实测：不会递归。OS 在 16~32 层就用 `ELOOP` 打回来，实际表现是一条超长路径的 stat 报错
（`too many levels of symbolic links`）。引擎不额外做环检测，靠这个。

代价是报错信息里那条路径很长很难看。不值得为它专门维护一套 inode 去重。

## 六. 变量名单只有一份，就是模版本身

**选了什么**：引擎任何地方都不收「变量名单」。`Ep.GetVarNameList()` 从模版算出这个入口文件
用到哪些变量，`Ep.Render(varMap)` 要求 `varMap` 的 key 集合跟它**完全一致**——少一个报错，
多一个也报错，值可以是空串。

**这一节曾经写的是相反的结论**，原话是「`Check(varNameList)` 和 `Render(varMap)` 是两份要
手工对齐的名单……接口的简单是有价值的，这个洞暂时不值那个价」。那个洞是：漏对齐一个名字，
Check 放行，到渲染真走到那个变量才炸，而且**只在恰好用到它的那个入口文件上炸**，别的入口文件
全渲染成功，人会以为没事。

当时**试过又否掉**的方案是「把名单挪进构造函数（`NewFromMap(fileMap, varNameList)`）+
Render 强制 key 集合跟全局名单一致」，否掉的理由是「构造函数多一个参数、Render 多一条
必须填全局名单的约束（哪怕某个入口文件用不到那个变量）」。

现在这个方案把那两条理由都绕开了：**构造函数不加参数**（名单不是输入，是算出来的结果），
**Render 只要求这个 ep 自己用到的那些**（不是全局名单）。净效果是接口更简单不是更复杂，
所以原来那个「不值那个价」的权衡不成立了。

**顺带消掉的东西**：

* `Render` 原来的第二个返回值 `usedVarNameList`。这个引擎没有条件也没有循环，同一个入口文件
  每次渲染用到的变量集合恒定——那是个**伪动态量**，用一个每次渲染重算的返回值表达一件渲染前
  就已知的静态事实。挪到 `Ep` 上是把假象改回事实。
* `Render` 里那两条「include 找不到」「同一棵树里重复 include」的报错。检查并进建包之后它们
  在渲染期不可达了，于是删掉（连带 `expandInto` 的 error 返回值），而不是留着当兜底。
* `Render` 里 `varMap == nil` 的特殊处理。老代码里 nil 在内部另有「只走结构不填值」的意思，
  得专门写几行防着调用方传 nil 被误当成那个模式。现在 nil 和空 map 都只是「key 集合为空」。

**「多给了也报错」是这套的关键一环**，它给调用方白送一条 fail-closed：模版里的 `{{linuxIp}}`
被人删了改成写死的 IP，渲染依然出得来一份通顺的提示词，光看字符串判断不出来——但调用方手写的
varMap 里还留着 `linuxIp` 这个 key，Render 当场报「多了」。这正是原来 `usedVarNameList`
存在的理由，现在不用调用方自己写那段判断了。

**代价**（明知的，两条）：

| 代价 | 缓解 |
|---|---|
| 一份 varMap 喂不了所有入口文件（原来 readme 明确写着「多给了不报错，否则等于逼调用方按入口文件拆 varMap」） | 拆的成本变了：`GetVarNameList()` 直接告诉你拆成什么样，不用调用方自己想 |
| 「模版用了个程序不认识的变量」不再是建包错误，降级成 Render 错误，而且一次只报一个 ep | 报错带上模版里用到它的**全部**位置；跨 ep 靠调用方在启动时遍历 `GetEpList()` 扫一遍（example/main.go 的 loadTpl，5 行） |

**还有一个用法上的坑**，写进 readme 七之一了：真正的调用点必须**手写** varMap 的 key 名单。
拿 `GetVarNameList()` 去驱动建 varMap 的话，varMap 会跟着模版一起缩，上面那条 fail-closed
就被消掉了。启动自检那种冒烟测试可以那么写，真正的调用点不行。

**什么能推翻它**：出现一个真实场景，同一份 varMap 确实该喂给多个用变量子集不同的入口文件，
而按入口文件拆开明确更差。到时候把「多给了报错」放宽成「只查缺的」是现成的改法——但那样
`usedVarNameList` 得加回来。

## 七. `NewFromMap` 不拷贝 `[]byte`

**选了什么**：传进来的 `map[string][]byte` 里的切片直接引用，不做防御性拷贝。

**代价**：调用方建包之后再去改自己那份切片，会改到模版内部已经解析好的内容，而且 `fileMap` 和
`tokenMap` 会对不上（token 是解析时算好的，不会跟着变）。

**为什么不防**：提示词包动辄几百 KB，而正常用法（`ScanDir` 读出来直接喂进来、或者 embed 的
只读字节）根本不会去改它。这条写进文档就够了，不为它付一次全量拷贝。

## 八. 报错里绝不贴整段正文

这不是一条规矩，是一类反复踩的坑，单独记一下。

模版报错常常要引用一小截原文帮人定位。危险在于「一小截」的边界如果是搜一个字符搜出来的，
那它可能一路搜到几十行之后：

- `{{...}}` 里找 `}}`：正文里写个 `{{` 讲 Vue，几十行后碰巧有个 `}}`，body 就是几十行正文。
  → 修法：body 含换行就不当变量名报，改报「`{{` 到行尾没等到 `}}`」，并用 `briefHead` 只取
  第一行的前 30 个字符。
- here doc 名字里找第二个 `|`：正文里写个 `{{|管道`，40 行后表格里有个 `|`，「名字」就是
  一大段正文，`%q` 一贴 3000 多字节。
  → 修法：名字只在**本行**里找。合法名字是「字母开头的字母数字」，本来就跨不了行。

**通用做法**：任何「从某个位置搜到某个字符」的边界，先想清楚搜不到会扫多远；报错里引用原文
一律走 `briefHead`（只取第一行、按 rune 截断到 30 个字符，不切坏 UTF-8）。

## 九. 报错顺序必须稳定

Go 的 map 遍历顺序是随机的。一批坏文件/坏路径，如果遍历 map 边走边 return，每次跑报的是随机
一条——人改了第一条重跑，看到另一条，会以为自己的改动生效了。

所以 `NewFromMap` 里**路径校验和解析这两个循环都走 `getSortedKeyList`**。
`runCheck` 里的 `refMap`、`msgList` 同理，`Ep.checkVarMapKey` 里报「多给了哪几个」那个循环也一样
（它遍历的是调用方的 `varMap`）。

加检查的时候记得跟上这条：新循环只要遍历 map 又会产出报错，就得先排序。
`TestNewFromMapPathErrorIsStable` 和 `TestRenderVarMapKeyErrorIsStable` 盯着这件事
（各跑 200 次，报错必须字节相同）。

## 十. 检查并进建包，没有逃生口

**选了什么**：`Check` 不再是一个单独的方法，它是 `NewFromMap` / `NewFromDir` 的一部分。
建得出来的 `Tpl` 就是全部检查都过了的 `Tpl`。

**为什么**：`Tpl` 从此只有一种状态。老接口有两种（解析过的 / 检查过的），而这两种在类型上
分不出来，全靠调用方记得调那一步——「忘了调 Check」是个真实的失败模式，README 和 example 都得
花篇幅教「先 New 再 Check 再全量渲染自检」三步。合并之后是一步。

顺带的收益比看上去大：合并之后，渲染期那些「include 找不到」「重复 include」的错误路径全部
不可达了，于是可以**删掉**（见第六节）。留着不可达的兜底不会让代码更对——兜底本身也会有 bug，
而且没法测。

**代价**：那些检查绕不过去。一个 600 字节以下的单调用者 part 会让整个包建不出来，没有
「我就想先渲染一下看看」这个口子。测试写 fixture 的时候也得让它是个合法的包（仓库里的
`padPart` 就是干这个的）。

这跟第二节的立场是一致的：那些检查本来就是「这么写一定是写错了」的断言，不是口味。既然不打算
让人关掉，就没理由留一条绕过去的路。

**什么能推翻它**：出现一个真实需求，需要在包还没修好的时候就渲染其中某个入口文件（比如某种
增量修模版的工具链）。目前没有。

## 十一. `NewFromDir` / `GetEp` / `Render` 各配一个 `Must` 版

**选了什么**：三个 `Must` 版，出错 `panic(err)`——panic 出来的就是原版那个 error 本身，
不包装、不改字。原版一个都不删，调用者按参数来源自己切。

**为什么**：这三处的 err 有个共同点。在最常见的那种用法下——参数是代码里写死的常量——它们
不是运行时状况而是**静态矛盾**：入口文件路径打错、`varMap` 的 key 集合跟模版对不上，都是
「同一个调用点要么永远成功、要么每次都失败」。`Render` 最典型：值是什么、有多长、内容多脏
都不影响成败，唯一的失败原因是 key 集合。这类 err 往上传没有意义，接住它的人也只会打印出来
退出，中间那些 `if err != nil` 只是缩进。

**代价**（两条，都是明知的）：

* 多三个导出符号，而且 panic 穿过了库边界。后者是有意的：panic 的值就是那个 error，
  `recover()` 之后 `r.(error)` 直接拿回来，没有信息损失。`must_test.go` 里三个用例分别
  拿原版的 error 比对，钉的就是「Must 版不吃信息、不改行为」。
* 三个里 `MustNewFromDir` 是最弱的一个：`ScanDir` 要碰文件系统，权限变了、symlink 断了、
  磁盘出错都是**真的运行时状况**，不是静态矛盾。它够格配 Must 版靠的是另一条理由——模版包
  通常是本程序自己的一部分，加载不了就没法继续跑。dir 来自命令行或用户输入时就该用原版。

**什么能推翻它**：有人把 Must 版用在参数其实来自运行时的地方然后线上炸了。那多半说明
「按参数来源切」这条判据在文档里没讲清楚，该改的是文档不是接口——除非发现这条判据本身
划不出清晰的界，那才该把某个 Must 版撤掉。
